# Michael–Scott MPMC queue — этап 1

Цель упражнения — реализовать неблокирующую FIFO-очередь для нескольких
производителей и нескольких потребителей. На этом этапе логическая
корректность алгоритма отделена от безопасной рекламации памяти.

## Интерфейс

Реализация находится в `MSQueue.h` и должна предоставлять:

```cpp
template <class T>
class MSQueue {
public:
    MSQueue();
    ~MSQueue();

    MSQueue(const MSQueue&) = delete;
    MSQueue& operator=(const MSQueue&) = delete;
    MSQueue(MSQueue&&) = delete;
    MSQueue& operator=(MSQueue&&) = delete;

    void push(T value);
    std::optional<T> try_pop();
};
```

Очередь используется только пока живы все обращающиеся к ней потоки.
Разрушать очередь одновременно с `push()` или `try_pop()` нельзя.

## Ограничения этапа

- Одновременно разрешены несколько producer и несколько consumer.
- `push()` и `try_pop()` не должны использовать mutex, spinlock или ожидание
  condition variable.
- Очередь должна хранить move-only типы.
- В основе очереди должен находиться фиктивный dummy-узел.
- `head` и `tail` — атомарные указатели и могут временно указывать на разные
  стадии одного изменения очереди.
- Поток, заметивший отставший `tail`, должен помогать продвинуть его.
- Удалённые узлы на этапе 1 нельзя освобождать до деструктора очереди. Это
  намеренная временная утечка памяти на протяжении жизни объекта, а не
  итоговая стратегия reclamation.
- Для первой корректной версии разрешено использовать
  `std::memory_order_seq_cst`. Ослабление memory order будет отдельным шагом.

Использование `new` не даёт строгой гарантии lock-free всему вызову: здесь мы
изучаем lock-free алгоритм очереди, считая allocator внешней зависимостью.

## Инварианты, которые нужно сформулировать до кода

1. Из `head` всегда достижим текущий dummy-узел.
2. Реальный элемент находится не в `head`, а в следующем узле.
3. Успешно присоединённый узел больше не отсоединяется от списка.
4. `tail` может отставать, но не должен указывать вперёд за последний
   присоединённый узел.
5. Только один consumer получает право переместить значение из конкретного
   узла.

## Вопросы для самопроверки

Перед реализацией запиши ответы рядом с кодом или в своих заметках:

1. Как выглядит состояние `head == tail`, но `head->next != nullptr`?
2. Какая операция является точкой линеаризации `push()`?
3. Какая операция является точкой линеаризации успешного `try_pop()`?
4. Где находится точка линеаризации неуспешного `try_pop()`?
5. Почему помощь в продвижении чужого `tail` не меняет FIFO-порядок?
6. Почему нельзя удалить старый dummy сразу после успешного изменения
   `head`?

Полезная гонка для разбора:

```text
P1 присоединил новый узел
P1 остановился до обновления tail
P2 увидел отставший tail
P2 продвинул tail
P2 присоединил следующий узел
```

## Что проверяют тесты

- пустое состояние и последовательный FIFO;
- заполнение после повторного опустошения;
- move-only значения;
- освобождение всех объектов деструктором;
- несколько producer с одним consumer, включая порядок каждого producer;
- один producer с несколькими consumer;
- смешанный MPMC-сценарий: каждый идентификатор возвращён ровно один раз.

Тест `multiple_producers_fifo` проверяет порядок каждого producer через одного
consumer. В MPMC-тесте намеренно не проверяется порядок, записанный разными
consumer после возврата из `try_pop()`: планировщик может задержать поток уже
после точки линеаризации и создать ложное впечатление нарушения FIFO.

## Сборка и запуск

Обычная проверка одной командой:

```bash
make test
```

Запуск одного сценария во время разработки:

```bash
make run TEST=sequential_fifo
```

Также доступны `make asan`, `make tsan`, `make clean` и `make help`.

Эквивалентные команды CMake вручную:

```bash
cmake -S . -B build -DENABLE_TSAN=OFF -DENABLE_ASAN=OFF
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Дополнительные проверки:

```bash
cmake -S . -B build-asan -DENABLE_ASAN=ON
cmake --build build-asan -j
ctest --test-dir build-asan --output-on-failure

cmake -S . -B build-tsan -DENABLE_TSAN=ON
cmake --build build-tsan -j
ctest --test-dir build-tsan --output-on-failure
```

Прохождение тестов необходимо, но не доказывает корректность lock-free
алгоритма. После реализации отдельно разбери инварианты, точки линеаризации,
все разыменования потенциально устаревших указателей и progress guarantee.
